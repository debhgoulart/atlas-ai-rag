# Atlas AI Constitution

## Core Principles

### I. Monorepo Architecture & Strict Separation of Concerns
Frontend and backend MUST operate as completely independent applications within the single repository.
- Backend (`/backend`) and frontend (`/frontend`) MUST NOT share code directly via relative imports or internal filesystem dependencies.
- Communication between frontend and backend MUST occur exclusively over HTTP REST APIs (`/api/v1`).
- Each application MUST maintain its own isolated dependency manifest (`requirements.txt`/`pyproject.toml` in backend; `package.json` in frontend) and independent `Dockerfile` to enable separate production deployments (e.g., Vercel for frontend and Render/Railway for backend).

### II. Clean Code, Strict Typing & Educational Value
As a portfolio and advanced learning application, Atlas AI code MUST serve as a benchmark for readability, maintainability, and architectural discipline.
- Strict typing is mandatory: Pydantic v2 schemas for all backend models and payloads; TypeScript interfaces and types for all frontend modules.
- Non-trivial technical decisions—especially concerning document chunking, vector indexing, similarity distance thresholds, and prompt formulations—MUST include educational docstrings explaining the technical rationale.
- Code MUST follow idiomatic patterns: FastAPI dependency injection and routers; Vue 3 Composition API with `<script setup>`.

### III. Strict API Contracts & Living Schemas
API contracts are the single source of truth governing integration between independent services.
- Every endpoint MUST define explicit Pydantic request and response schemas; unstructured or dynamic dictionary payloads are prohibited.
- Frontend HTTP services MUST strictly mirror backend API contracts using TypeScript types to ensure end-to-end type safety and prevent runtime serialization bugs.
- Endpoints MUST follow standard REST semantics, consistent HTTP status codes (200, 201, 204, 400, 401, 403, 404, 422, 500), and predictable URL naming conventions under `/api/v1/`.
- OpenAPI/Swagger documentation generated by FastAPI MUST remain valid, documented, and testable at all times.

### IV. Multi-Tenant Data Isolation & Server-Enforced Security (NON-NEGOTIABLE)
All private resources MUST have explicit server-enforced ownership and strict multi-tenant access control. Under no circumstance may any user's data be exposed, retrieved, modified, or deleted by another user without explicit, verified authorization.
- **Server-Derived Identity**: The `user_id` utilized for authorization and query scoping MUST be extracted exclusively from verified backend authentication credentials (e.g., cryptographic JWT claims or server-managed sessions). Client-provided user identifiers in request headers, query parameters, or request bodies MUST NEVER be trusted for data scoping or ownership validation.
- **Explicit Resource Ownership**: Every private entity—including folders, documents, text chunks, vector embeddings, chat conversations, and message histories—MUST maintain an explicit, indexed relationship to the owner (`user_id`). Every folder MUST belong to a single user; every document belongs to the uploader; every chat session belongs to its creator.
- **Scoped Database & Vector Queries**: All SQL/ORM queries and vector similarity searches (`pgvector`) MUST explicitly filter by the authenticated `user_id`. A user MUST NEVER retrieve, match, or infer documents or embeddings belonging to another user, regardless of semantic similarity scores or query formulations.
- **Server-Side Access & Mutation Validation (IDOR Defense)**: Endpoints performing creation, retrieval, updates, or deletions MUST validate that the target resource belongs to the authenticated user before executing the operation. Direct manipulation of resource IDs (Insecure Direct Object Reference) MUST result in an access denial (HTTP 403 Forbidden or HTTP 404 Not Found to prevent resource enumeration).
- **Fail-Closed Authorization**: The absence, expiration, or invalidity of an authenticated `user_id` MUST immediately abort the request and block any operation requiring data ownership. Anonymous access to private user resources is prohibited.
- **Frontend Session Hygiene & Defense in Depth**: While the frontend is NEVER considered a security boundary, client applications MUST enforce strict session hygiene. Logging out or switching accounts MUST completely purge all cached user data (including Pinia stores, `localStorage`, `sessionStorage`, and Axios cached headers) to prevent cross-account data leakage in shared browser environments.
- **Secrets Management**: Secrets, API credentials (such as `GEMINI_API_KEY`), and database connection strings MUST NEVER be committed to version control. All secrets MUST be loaded via environment variables using `.env` files, paired with audited `.env.example` templates.
- **Input & Upload Defense**: File uploads MUST enforce strict validation (whitelisted MIME types: PDF, TXT, Markdown; size limits; filename sanitization to prevent path traversal). Database interactions MUST employ parameterized queries and ORM mappings to prevent SQL injection.

### V. Responsible AI Engineering, Grounded RAG & Anti-Hallucination
The application MUST implement rigorous guardrails ensuring reliable, verifiable, and safe AI interactions.
- **Context Grounding**: System prompts MUST instruct the LLM to synthesize answers exclusively from the retrieved document chunks. When retrieved passages lack sufficient information, the model MUST explicitly acknowledge the gap rather than extrapolating or inventing facts.
- **Source Attribution**: Chat responses MUST return reference metadata for every cited source, including source document title, chunk index or page number, and similarity score.
- **Prompt Injection Defense**: Ingested document content MUST be treated as untrusted data, enclosed within strict delimiter tags (e.g., `<context>...</context>`), preventing adversarial document instructions from hijacking the system prompt.
- **Observability**: Token consumption, generation latency, and similarity retrieval scores SHOULD be logged for auditability and cost management.

### VI. Architectural Simplicity (KISS/YAGNI) & Conscious Framework Usage
Maintain clear, maintainable implementations without unnecessary layers of abstraction.
- The core RAG pipeline (document ingestion, text chunking, embedding generation via Google Gemini `text-embedding-004`, vector persistence/indexing via `pgvector`, cosine similarity retrieval, and context augmentation) MUST be built natively and transparently.
- Third-party orchestration frameworks (such as LangChain) MUST be employed only when they deliver clear, demonstrated technical value that cannot be achieved cleanly with native code. Any framework adoption MUST be justified.

### VII. Pragmatic Testing Pyramid & Testability
Quality assurance MUST be integrated into each development stage.
- **Unit Tests**: Fast, isolated tests for parsing algorithms, text chunkers, and Pydantic schema validation.
- **Integration Tests**: Verification of database repositories, `pgvector` similarity queries, and FastAPI endpoint handlers.
- **RAG Evaluation**: Qualitative checks verifying retrieval recall and grounded response generation.
- External dependencies (LLM APIs, embedding endpoints) MUST be easily mockable via dependency injection during automated test execution.

### VIII. Standardized Error Handling & Structured Observability
The application MUST fail gracefully and provide actionable diagnostics.
- The backend MUST return standardized error responses containing a readable message (`detail`), an application-specific error code (`code`), and optional contextual data.
- Structured logging MUST capture operational events, request timings, and external API error states without logging sensitive tokens or confidential document contents.
- Network timeouts, rate limits, and external service downtimes (e.g., Gemini API errors) MUST be handled resiliently with informative user feedback in the frontend.

### IX. Technical Documentation & Architectural Decision Records (ADRs)
Technical choices MUST be documented transparently to maximize learning and architectural clarity.
- Significant design choices MUST be recorded as Architectural Decision Records (ADRs) under `docs/adr/`.
- Required initial ADR topics include: choice of pgvector similarity metric (Cosine vs Inner Product/L2), text chunking and overlap parameters, embedding dimension and model selection, and frontend state management conventions.
- The project root MUST maintain a clear `README.md` guiding installation, environment setup, local execution, and test runs.

### X. Incremental Specification-Driven Development (Spec Kit Flow)
Feature development MUST strictly adhere to the Spec Kit lifecycle:
1. **Specify** (`/speckit-specify`): Define business requirements, user scenarios, and functional boundaries.
2. **Clarify** (`/speckit-clarify`): Identify and resolve ambiguities prior to implementation.
3. **Plan** (`/speckit-plan`): Establish technical design, data models, and API contracts.
4. **Tasks** (`/speckit-tasks`): Decompose work into atomic, dependency-ordered, and testable tasks.
5. **Implement** (`/speckit-implement`): Execute tasks incrementally with continuous validation.
- No feature code shall be added without an approved specification and task breakdown.

### XI. Version Control Hygiene & Atomic Preservation
The repository history MUST remain clean, intentional, and traceably structured.
- Commits MUST follow the Conventional Commits specification (`feat:`, `fix:`, `docs:`, `refactor:`, `test:`, `chore:`).
- Commits MUST be atomic and created only upon explicit user confirmation.
- Preexisting files, configurations, and tools MUST be preserved; no breaking overwrites or deletions shall occur without prior approval.

## Technology Stack & Development Environment Constraints

### Backend
- **Language**: Python 3 (3.11+ / 3.14 compatible).
- **Environment**: Isolated Python virtual environment (`.venv`) with managed dependencies.
- **Framework**: FastAPI with asynchronous endpoints.
- **Data & ORM**: SQLAlchemy 2.0 (async), Pydantic v2, Alembic for schema migrations.
- **Vector Search**: PostgreSQL with `pgvector` extension.

### Frontend
- **Framework**: Vue.js 3 with Composition API (`<script setup>`).
- **Language**: TypeScript (strict mode enabled).
- **Tooling & Build**: Vite.
- **State Management**: Pinia.
- **Routing**: Vue Router 4.
- **Styling & UI**: Tailwind CSS, Lucide Vue Next icons.
- **HTTP Client**: Axios with configured interceptors.

### AI & Vector Pipeline
- **LLM Provider**: Google Gemini API (Gemini 2.5 Flash / Pro).
- **Embedding Model**: Google Gemini `text-embedding-004` (768 dimensions).
- **Vector Database**: PostgreSQL + `pgvector` (Cosine Distance index).
- **Orchestration**: Direct, native Python service implementations; LangChain only when demonstrably beneficial.

### Infrastructure & Deployment
- **Local Development**: Docker and Docker Compose managing PostgreSQL with pgvector, backend, and frontend.
- **Version Control**: Git / GitHub (`git@github.com:debhgoulart/atlas-ai-rag.git`).
- **Production Targets**: Vercel for frontend static hosting; Render or Railway for backend containerized service (subject to technical validation).

## Development Workflow & Quality Gates

### Quality Gates
- **Type Safety**: Backend validation via Pydantic; Frontend verification via `vue-tsc` / TypeScript compiler.
- **Linting & Formatting**: Clean code standards enforced across Python and Vue/TypeScript files.
- **Testing Gate**: Unit and integration test suites must pass before merging feature branches.
- **Security Check**: No `.env` secrets or raw credentials permitted in staging or commits.
- **Multi-Tenancy & Data Isolation Gate**: All endpoints, database queries, mutations, and vector searches handling private data MUST have automated multi-user test coverage verifying that User B cannot view, edit, delete, or vector-match User A's resources.
- **Documentation Gate**: Every new API endpoint or structural change must be documented in OpenAPI and reflected in project documentation.

## Governance

- **Supremacy**: This Constitution supersedes all ad-hoc conventions and informal practices.
- **Amendments**: Amendments require an explicit proposal detailing the rationale, impact analysis, incrementation of the semantic version, and formal approval.
- **Versioning Policy**:
  - **MAJOR**: Breaking changes to core principles, governance rules, or fundamental architectural separation.
  - **MINOR**: Addition of new principles, sections, or materially expanded guidelines.
  - **PATCH**: Typo corrections, wording refinements, and non-semantic clarifications.
- **Compliance**: All specifications, task lists, code implementations, and pull requests must verify compliance with this Constitution before ratification.
